## RSA – 연계 전문 처리 시스템

### 1. 🔍 배경

은행 시스템은 외부 기관(예: 금융결제원, 신한금융망, 한국은행 등)과의 통신이 필수야.  
하지만 외부 시스템은 내부 시스템과 포맷이나 프로토콜이 달라.  
그래서 중간에 **연계 시스템(RSA)**가 있어야 서로 "알아듣는 말로" 대화가 가능해져.

---

### 2. 🧠 개념 요약

|개념|설명|
|---|---|
|**전문(Message)**|정해진 포맷의 데이터 송수신 구조. ISO20022, 고정폭 등|
|**RSA**|전문을 설계하고, 송수신하고, 변환(mapping)하고, 이력을 관리하는 툴|
|**연계 로직**|내부(DEVON 등)와 외부(기관) 간 인터페이스 연결|
|**연계 트랜잭션 ID(OP)**|RSA 내에서 관리하는 전문 송수신 단위 ID|

---

### 3. 🧱 RSA 구성요소

|구성요소|설명|실무 예시|
|---|---|---|
|**AMCD**|연계 업무 단위 모듈|`AMCD_FN_ORG` 등|
|**OP (Operation)**|하나의 송수신 전문 단위 (전문 ID)|`OP_TR_SEND`|
|**DTO**|전문을 구성하는 데이터 구조 (VO 같은 것)|`TR_SEND_DTO`|
|**Mapping (매핑)**|내부 데이터 ↔ 외부 전문 매핑 정의|입력 매핑, 출력 매핑|
|**Header/Body**|전문 구분. Header: 공통정보 / Body: 업무 데이터|ISO20022의 `<AppHdr>`와 `<Document>` 구분|

---

### 4. 🛠 실무 흐름 예시

**[1] 업무 요청 흐름 (예: 송금)**

plaintext

복사편집

`1. iDev 화면에서 버튼 클릭 → setTranID("TR_51620011") 2. DEVON에서 내부 로직 처리 3. RSA 연계 모듈 호출 (AMCD, OP) 4. 전문 생성 (DTO 기반 + Mapping) 5. 외부 기관으로 전문 송신 6. 응답 수신 → 매핑 처리 → 결과 DEVON으로 리턴 → 단말 표시`

**[2] 실무 폴더 구조**  
RSA에서 열면 보통 이런 식으로 돼 있어:




~~~
AMCD_FN_ORG   └─ PBI_SEND_TR        ├─ DTO        ├─ OP        │   ├─ 송신전문(OP_XXXX_SEND)        │   └─ 수신전문(OP_XXXX_RECV)        ├─ Mapper        │   ├─ Inbound (내부 → 전문)        │   └─ Outbound (전문 → 내부)
~~~

---

### 5. ⚙️ 전문 등록/매핑 실무 팁

- **DTO는 VO랑 비슷한 개념**으로, 필드명과 자료형을 정확하게 맞춰야 함
    
- 전문 포맷이 XML이면 XPath로 매핑하고, 고정폭이면 바이트 오프셋을 설정
    
- **Inbound**는 내부 시스템 → 외부 전문
    
- **Outbound**는 외부 전문 → 내부 시스템

## [[RSA 구성요소]] 정리 – AMCD, PBI, EBI, DTO 등

### 🧱 1. AMCD (Application Component Definition)

|항목|설명|
|---|---|
|의미|연계 업무 하나의 **기능 단위 컴포넌트**|
|역할|하나의 연계 업무 단위를 구성하는 컨테이너 역할|
|실무 예|`AMCD_ISO_FUND_TRANSFER` – ISO 송금 연계 모듈 전체|
|생성 위치|RSA 내 연계 모듈 구성의 **최상위 단위**|
|내부 포함|PBI, EBI, DTO, OP, Mapper 등 포함|

> **비유하자면 AMCD는 폴더고, PBI/EBI/DTO는 그 안의 파일들이야.**

---

### ⚙️ 2. PBI (Process Business Interface)

|항목|설명|
|---|---|
|의미|내부 → 외부 송신을 처리하는 **연계 송신 모듈**|
|구성요소|내부 요청 DTO → 매핑 → 외부 전문(OP) 송신|
|실무 흐름||

1. DEVON 등에서 RSA 호출 (내부 데이터)
    
2. PBI가 호출됨
    
3. 내부 → 외부 DTO 매핑 (Inbound Mapping)
    
4. 송신 전문(OP) 생성 → 외부 기관 송신  
    | 예시 | PBI_FUND_SEND
    

---

### ⚙️ 3. EBI (External Business Interface)

|항목|설명|
|---|---|
|의미|외부 → 내부 수신을 처리하는 **연계 수신 모듈**|
|구성요소|수신 전문(OP) → 매핑 → 내부 DTO 반환|
|실무 흐름||

1. 외부 기관에서 전문 수신
    
2. EBI가 자동 호출됨
    
3. 전문 데이터 → 내부 구조로 변환 (Outbound Mapping)
    
4. 내부 응답 DTO 반환 → DEVON 등으로 전달  
    | 예시 | EBI_FUND_RECV
    

> 보통 PBI는 **요청 처리**, EBI는 **응답 처리**에 대응돼 있어. (비동기일 경우 특히 중요)

---

### 📦 4. DTO (Data Transfer Object)

| 항목    | 설명                                       |
| ----- | ---------------------------------------- |
| 의미    | RSA 내에서 송수신 전문에 담기는 **데이터 구조체**          |
| 구조    | JAVA Bean과 유사한 getter/setter 있는 VO 형태    |
| 구분    | 요청 DTO, 응답 DTO 나눠서 생성                    |
| 필드 구성 | 전문 필드와 정확히 일치해야 함 (예: 고객ID, 금액 등)        |
| 예시    | DTO_Req_TransferInfo, DTO_Res_ResultInfo |


## [[RSA 시스템명세모델 폴더구조 설명]]

폴더 경로:  
`JBA_MODEL_VEI_PIC(부대업무) > 2.시스템명세모델`

---

### **01. 공용DTO정의**

|항목|설명|
|---|---|
|의미|시스템 전반에서 재사용되는 **공통 DTO들**|
|예시|고객정보Dto, 계좌기본정보Dto, 에러응답Dto 등|
|실무 사용처|여러 연계 모듈에서 반복 사용되는 구조를 여기서 정의하고 참조함|

> 공통 필드 구조를 매번 새로 만들 필요 없이 여기서 관리하는 걸 가져다 씀.  
> RSA뿐 아니라 DEVON, 화면에서도 사용할 수 있음.

---

### **02. 업무선후처리**

|항목|설명|
|---|---|
|의미|연계 송수신 전/후에 필요한 공통 처리 모듈|
|예시|전처리: 로그 기록, 전문 ID 검증 / 후처리: 응답 로그 저장|
|실무 사용처|특정 연계 업무마다 요청 전에 추가 검증이 필요하거나, 응답 후 후처리가 필요할 때 여기에 정의한 공통 모듈을 연결함|

> PBI나 EBI에서 업무 처리 전후로 이걸 호출해서 공통 기능 수행.

---

### **03. 프로세스컴포넌트**

|항목|설명|
|---|---|
|의미|**업무별 연계 모듈이 실제 구현되는 공간**|
|예시|`신한금융망전문관리`, `거래코드관리[PBI]`|
|실무 사용처|연계 단위별 AMCD, PBI, DTO, 매핑 등을 여기에 생성함|

> **네가 실제 개발하는 대부분의 작업이 여기서 이루어짐.**

---

### **04. 공통프로세스컴포넌트**

|항목|설명|
|---|---|
|의미|여러 연계 업무에서 공통으로 참조하는 프로세스 모듈|
|예시|전문 에러코드 처리, 공통 전문 변환기 등|
|실무 사용처|개별 업무가 아닌, 여러 업무에서 같이 참조되는 연계 기능을 구현할 때 사용함|

> 자주 반복되는 구조/로직을 따로 모아놓은 공용 프로세스 영역.

---

### **05. 엔터티컴포넌트**

|항목|설명|
|---|---|
|의미|DB의 테이블 구조를 기반으로 만든 **Entity 객체** 정의|
|실무 사용처|RSA에서 DB에 직접 접근하는 일이 거의 없지만, 필요한 경우 DB엔터티가 정의돼 있음 (예: 마스터 테이블 조회)|

> 보통은 DEVON에서 더 많이 활용되지만 RSA에서도 가끔 참조함.

---

### **06. 배치컴포넌트**

|항목|설명|
|---|---|
|의미|주기적으로 수행되는 배치(일괄) 업무 처리 컴포넌트|
|예시|매일 새벽 자동 송신 / 이력 정리 배치 등|
|실무 사용처|특정 시간에 연계 전문을 자동 전송해야 할 때 사용 (예: 일일 마감 송신)|

> 실시간 연계가 아닌 **예약/자동 실행 처리**에 해당됨.

---

### **07. 연동컴포넌트**

|항목|설명|
|---|---|
|의미|내부 시스템과 외부 시스템 사이의 연결 정의 (인터페이스 정의)|
|실무 사용처|RSA가 외부 시스템과 어떤 방식으로 연동하는지 정의됨 (프로토콜, 경로 등)|

> 전문이 어디로 어떻게 나가야 하는지, 포트나 경로 정보가 설정됨.

---

### **10. 디퍼드컴포넌트**

|항목|설명|
|---|---|
|의미|Deferred 방식(지연처리) 연계에 사용하는 컴포넌트|
|실무 사용처|전문 응답을 바로 받지 않고, 나중에 처리되는 케이스에 사용 (비동기 처리 구조)|

> 예: 외부 시스템이 응답을 수초~수분 뒤에 주는 경우.

---

### **99. 유스케이스 실현**

|항목|설명|
|---|---|
|의미|UML 기반 Use Case 실현 시나리오 정의 (아키텍처 문서용)|
|실무 사용처|설계 단계에서 연계 업무 흐름을 정리하거나 설명할 때 작성함|

> 문서 목적. 실코딩보단 설계와 문서화용 폴더야.
